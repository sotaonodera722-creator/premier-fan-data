# 日曜朝のプレミアリーグ — 製品仕様

> 日曜の朝に10分開けば、週末に何が起きたか・日本人選手がどう関わったか・今夜どの試合を観るべきかが、
> すべて日本語でわかるサイト。速報サイトでもデータベースでもなく、**週に一度開く習慣の場所**。

- データ基準日: 2026-09-07（第3節終了時点、30 / 380 試合）
- 40機能 / 13スプリント（S13 は計画外の差し込み）
- 閲覧用ページ: https://claude.ai/code/artifact/ae7b14dd-99f2-41c1-b0f4-5b179c2cbf7c

## 1. 読者は4層に分かれる

「ライトなサッカーファン」では粗すぎる。障壁が層ごとに違い、最大の壁は全層に共通して
**「クラブが何者か分からない」** の一点に集約される。

| 層 | 誰か | 詰まるところ |
|---|---|---|
| **A** 日本人選手だけを追う人 | 三笘・遠藤の名前で検索して来る。プレミアリーグ自体はほぼ白紙 | クラブの区別がつかない。「ブライトン」がどこの何かも、強いのか弱いのかも分からない。順位表を見ても数字が意味に変換されない |
| **B** サッカーは好きだがプレミアは追えていない | W杯は観る。プレミアで知っているクラブは5つ程度 | 今シーズン何が起きているのかの文脈がない。誰が強いのか、何が異変なのかが分からない |
| **C** かつて観ていたが離れた | ファーガソン／ヴェンゲル時代は知っている | 浦島太郎状態。今の順位表には Hull City・Coventry City・Ipswich Town・Sunderland・Leeds が並び、Wolves も West Ham も Leicester もいない。しかも Hull City が2位。知っている地図が通用しない |
| **D** 今も観ている | 深夜に起きて観る層。主客ではない | 日本語のデータ源として使う。速報性も分析の深さも他に劣るので、ここを狙いにはしない |

狙いは **A → B → C の変換**。

## 2. サイトが担う3つの役割

- **翻訳機** — 英語のプレミアリーグ世界を日本語にする。名前だけでなく、順位表の数字を「意味」に変換することを含む
- **文脈供給機** — 「Hull City が2位」がなぜ驚きなのかを説明できる状態にする。データは持っているのに現状これができていない
- **定点観測の場所** — 週に一度、決まった時間に開く習慣。4時間更新では速報に勝てない以上、勝てるのはリズムの設計だけ

## 3. 構造的な発見：日曜の朝は節の途中

第3節のキックオフを日本時間に直すと、土04:00 → 土20:30〜23:00（5試合）→ 日01:30 → 日22:00 → 月00:30 と並ぶ。
つまり日曜の朝に開く瞬間は、**構造的に節が終わっていない**。

これは「週末が終わった後のまとめ」ではなく **「追いつきながら、今夜観る試合を選ぶ」場面** だということ。
トップページは終わった試合とこれからの試合を同じ強さで並べる必要がある。

## 5. デザインの方向 — スポーツ紙面

S13 までで中身は揃った。ここから先の見た目の基準を、感想ではなく規則として置く。

### 現状の診断 — なぜテンプレート的に見えるのか

S13 終了時点の画面を375pxで通して見て特定した、5つの原因。**すべて S14 以降で潰す。**

1. **日本語に書体が指定されていない。** `layout.tsx` が読むのは Geist と Rajdhani で、
   どちらも `subsets: ["latin"]`。**このサイトの主言語である日本語は端末任せ**で、
   Windows は游ゴシック、iOS はヒラギノ、Android は Noto になる。同じページが端末ごとに
   別の顔になり、游ゴシックの太字は線が細くて見出しが締まらない。文字が9割を占める
   サイトで書体を決めていない以上、他を何本直しても質は上がらない
2. **「英語の小見出し＋日本語の大見出し」が全ページで繰り返される。** `SCORERS` /
   `ASSISTS` / `TIMELINE` / `EXPECTED GOALS` など、ホームだけで10回。情報を足していない
   装飾であり、テンプレート的AIデザインの署名そのもの
3. **すべてが同じ角丸カード。** 順位表20行、ランキング3ブロック、タイムライン12行が
   等しく `rounded-xl border`。CLAUDE.md が禁じる「均質なカードの羅列」に自分でなっている
4. **数字が主役になっていない。** 得点ランキングの「3」と選手名が同じ大きさ。順位表では
   「勝点」の2文字が20回繰り返され、肝心の数字が小さい
5. **区切りを全部「線」でやっている。** 線が多いほど素人に見える。紙面は余白と整列で
   区切り、罫線は最後の手段として使う

### 目指す方向 — スポーツ紙面

英国紙のスポーツ面に近い、静かで数字が主役の組版。**かっこよさは装飾ではなく、
文字組みと余白の精度から出す。**

- **太いインク黒と、圧倒的な数字のサイズ差**で階層を作る。装飾では作らない
- **罫線を減らし、余白と整列で区切る**
- **数字は等幅（tabular）で縦に揃える。** 順位表・スタッツは桁が揃って初めて読める
- **繰り返しの単位を変える。** 20行が同じ見え方をするなら、それは表であってカードではない

### 破ってはいけない制約

- **モノクロ方針は維持する**（`globals.css` の方針コメント）。色はクラブのアイデンティティにのみ使う
- **ダークモードは当面入れない。** トークンは一箇所に集約されているので後から入れられる。
  方向が固まる前に検査の手間を2倍にしない
- **375pxで横スクロールしない**（R1）。紙面的な組版は幅を要求しがちなので、ここが最初に壊れる
- **一度に全ページを作り直さない。** 1スプリント＝1ページ。方向が違ったときの手戻りを小さくする

## 6. スプリント計画

各スプリントは1テーマ。番号は計画順で、S01〜S09 はこの順に実行した。S13 だけは計画外の差し込みで、
番号は最後だが実行は S09 の直後（S10 の前）。既知課題7件は S03・S04・S05 で全て消化する。

**S01〜S13 は実行済み。** S11 までで機能は揃い、S12（順位の推移を中心とした蓄積）と、
S14〜S18（デザイン）が残っている。

**S14 以降はデザインのスプリントで、1スプリント＝1ページとする。** 一度に全ページを
作り直さない理由は §5 に書いた。実行順は **S14（土台）→ S15（順位表）→ 代表の判断 →
S16・S17・S18**。S12 の位置は S15 の判断時に決める（10節を超えていることが条件）。

### S01 — 日本語であること（全層）

**含む**: 20クラブの日本語名（正式・略称）を全ページで使う / 日本人選手9人の漢字表記 / ポジション表記と国籍68カ国の日本語化 / 対訳がない選手が英語のままでもレイアウトが崩れないこと

**含まない**: 548選手全員のカタカナ化（S11） / スタジアム名の日本語化（S11） / 検索の日英両対応（S11） / 見た目のデザイン変更

**理由**: クラブ名は20件で確定作業として完結し、効果が全ページに波及する。ここを先に終えないと、以降どのスプリントで作る画面も英語混じりで生まれる。

### S02 — 日本時間と、信用の土台（全層）

**含む**: 全ページの日時を日本時間へ統一 / 深夜キックオフの誤読を防ぐ表記 / 「今夜」「明日未明」などの相対表現 / 最終更新日時・出典・4時間更新であることの明示 / 母数の明示と導出値の注記

**含まない**: 週末サマリーそのものの再設計（S05） / ユーザーがタイムゾーンを選べるようにすること

**理由**: 「日曜の朝」という製品の中心概念は日本時間でしか成立しない。S05で週末サマリーを作り込む前に時間軸を正しくする。信用の土台も同時に置く。

### S03 — 順位表を信用できるものにする（全層）

**含む**: 消化試合数のカラム（既知課題） / 同着を正しく扱う降格圏・CL圏・EL圏バッジ（既知課題） / モバイルでのチーム名の省略解消・順位表側（既知課題） / 各圏が何を意味するかの説明 / 得失点差の符号、フォーム表示の整理

**含まない**: 順位表の並び替え・絞り込み / FIXTURESの省略問題（S04） / 順位予測

**理由**: 順位表の数字が間違って見えることは、他のどの機能の魅力よりも信頼を損なう。降格圏バッジが3枠のうち2つにしか付いていないのは、現に間違った情報を出している状態。

### S04 — 片手で読める（シーンA）

**含む**: 選択中の節ピルが必ず画面内に見えること（既知課題） / 節切替の即時反映・URL反映の1秒遅延の解消（既知課題） / FIXTURESのチーム名の省略解消（既知課題） / 全ページの横スクロール撲滅とタップ領域の確保 / 「今節へ戻る」動線

**含まない**: 新しい画面や機能の追加 / デザインの刷新 / PC向けレイアウトの最適化

**理由**: 読者は布団の中で片手でスマホを持っている。ここが不快だと以降どんな良いコンテンツを載せても読まれない。既知課題をここで全て消化しバックログを空にする。

### S05 — 日曜の朝の10分（シーンA・B）

**含む**: 週末サマリーの完成。終了分と残り分を同じ強さで / 「10試合中8試合終了、残りは今夜22:00と明日00:30」の状態表示 / KPIタイル4枚の作り替え（既知課題） / 日本人選手の4状態分類（ベンチ入り出番なし／メンバー外の区別を追加） / スクロールなしで全10試合が把握できること

**含まない**: 見どころピック（S08） / 次節プレビュー（S10） / 試合詳細ページの改修（S08）

**理由**: S01〜S04で土台が整ったところで製品の中心体験を作る。ここが完成した時点で「日曜の朝に開く価値がある」が成立する。

### S06 — クラブが何者かを知る（層A・C）

**含む**: クラブ名鑑20（街、スタジアム、創設年、クラブカラー、歴史的な立ち位置） / 昇格組バッジ / クラブ立ち位置の分類 / 順位表・試合一覧・選手ページからクラブ名鑑への導線

**含まない**: チームスタイルの数値分析（S10） / ライバル・因縁マップ（S10） / クラブの歴史記事・年表

**理由**: **前回の仕様で完全に欠落していた柱。**「Hull City が2位」に驚けないのは、Hull City が何者か知らないから。層Cの浦島太郎問題と層Aのクラブ識別問題に同時に答える唯一の機能群で、これがないと以降の分析系機能はどれも土台なしに載ることになる。

### S07 — 先週から何が変わったか（シーンA）

**含む**: 順位の上下と勝点差の変化 / 今節を1文で要約（自動生成） / 順位表への変動インジケータ / 日本人選手の前節比

**含まない**: シーズン全体の推移グラフ（S12） / 過去シーズンとの比較（データがない） / 予測・見通し

**理由**: 週次で開く習慣の場所を名乗るなら、前回訪問との差分が要る。現状の仕様にはこれが1つもなかった。順位表を「今の状態」から「動いているもの」に変える。

### S08 — 選ぶ、そして観る（シーンB）

**含む**: 見どころピック3試合（ルールベース、根拠を数値付きで日本語表示） / 試合ダイジェストの整理（タイムライン、フォーメーション、xGとスコアの乖離） / 日本人選手のタイムライン上での強調 / これからの試合でも予想フォーメーションとH2Hで観る価値を判断できること

**含まない**: ハイライト動画・記事 / 選手個人の詳細スタッツ（データがない） / チームスタイル分析（S10）

**理由**: 週末サマリーで「気になった」読者を受け止める先を作る。見どころピックと試合ダイジェストは対で、片方だけでは効かない。選出は完全にルールベースにして、手書き運用が入って更新が止まる事態を避ける。

### S09 — その選手はレギュラーなのか（層A → B）

**含む**: 出場時間の節ごとの推移 / チーム内序列（同ポジション・同クラブの選手との比較） / チーム総試合時間に対する出場割合（不動／ローテーション／出番待ち） / 試合ごとの出場履歴とゴール・アシストの発生時刻 / 次の出場予定

**含まない**: 選手の写真 / 移籍・負傷・出場停止 / パス数・走行距離など個人スタッツ（いずれもデータがない）

**理由**: 「三笘が出た」の次に読者が知りたいのは「三笘はレギュラーなのか」。この問いには既存データで答えられる。層Aを層Bへ押し上げる中間の踏み台。

### S10 — リーグの構図が見える（層B → C）

**含む**: チームスタイル分析（39カテゴリからリーグ平均比で性格づけ） / 残留争い・優勝争いの構図 / ライバル・因縁マップ / 次節プレビュー / 母数の明示と少ないサンプルでの断定回避

**含まない**: 選手個人のスタイル分析（個人スタッツがない） / 戦術の図解・解説記事 / 勝敗予想・優勝確率

**理由**: 製品ゴールの本命。39カテゴリのスタッツは最大の未活用資産で、これがあると「マンチェスター・シティは何が違うのか」に日本語で答えられる。ただし S06 でクラブが何者か伝わっていないと、分析だけ出しても届かない。

### S11 — 置いていかない（層A）

**含む**: 用語解説（その場で読める短い日本語、別ページへ飛ばさない） / プレミアリーグの基本ルールの説明 / 出場実績のある選手のカタカナ表記への拡張とスタジアム名の日本語化 / 検索・絞り込みの日英両対応 / ランキングの同順位処理と導出値注記の整備

### S12 — シーズンを蓄積する（シーンC）

**含む**: **順位の推移（全38節）** / 節アーカイブ / シーズン通算での日本人選手の推移 / 比較ツールの整理 / 推しクラブ診断

**含まない**: エクスポート機能 / ユーザーアカウント・お気に入り（過去シーズンのデータは取得可能と判明したので除外理由でなくなった。S13 を参照）/ 時間帯の傾向（後述の保留）

**理由**: 現時点で3節分しかないので序盤に作っても中身が空。10節を超えたあたりから価値が出る。最後に置くのが合理的。

**中心は順位の推移。** `matches.json` は380試合すべての枠を持ち、消化済みの結果には
`matchday` と両クラブの得点が入っている。つまり**各節終了時点の順位表は、追加のデータ取得なしに
結果から再構成できる**。いま順位について言えるのは S07 の「前節比の▲▼」だけで、
シーズンの物語がない。ハル・シティが3位にいることの意味は、1点の推移で初めて伝わる。

再構成した履歴は、表示以外にも効く。現在の「前節比」はフィードの `previousPosition` に
依存しており、R8 の事故（表示順位と変動の基準のずれ）はその二重構造から出た。
自前で全節を持てば、基準を一本にできる。

### S13 — 昨季から何が変わったか（層B・C）〔計画外・実行済み〕

**含む**: 昨季の最終順位の取得（1部・2部） / 順位表ページの「昨季から何が変わったか」 / 昇格組の2部順位 /
降格した3クラブの明示と日本語名 / クラブ詳細ページの「昨季」

**含まない**: 過去シーズンの試合スタッツの埋め戻し（取得は可能だが1日100リクエスト制限で5日前後かかるため見送り） /
2022/23 以前（プラン外で403） / 順位表本体への昨季比の追加

**理由**: このスプリントは計画になかった。「今季の異変表示」を **不可** と判定していたのが誤りで、
football-data.org から 2023/24 以降の最終順位表が取れることが実データで判明したため、S10 の直前に差し込んだ。

判定を誤ったまま進めると、製品の中心命題（「Hull City が上位にいるのはなぜ驚きなのか」）に
最も直接答える数字を、取れるのに使わないまま12スプリントを終えることになる。実装コストは静的JSON1本と
1セクションで、S10 以降のどの機能よりも安い。順位表本体には入れていない — ▲▼ は S07 で「前節比」の
意味を持っており、同じ記号を別の基準点で使うと1つの記号が2つの意味を持つため。

### S14 — 書体と階調を決める（全層・土台）

**含む**: 日本語書体の指定（現状ゼロ）/ 数字書体の決定 / 文字サイズとウェイトの段階を数値で定義 /

`globals.css` へのトークン追加

**このスプリントでは見た目はほとんど変わらない。** それでよい。土台だけを置く。

検証は「トークンが定義されたか」ではなく、**既存の全ページが壊れていないこと**で行う。
書体を入れ替えると行の高さが変わり、375pxの横スクロールと切れが最初に壊れる（R1・R9・R10）。

## 7. デプロイ1本に容量の予算がある（2026-09-10 に判明）

4時間更新と同じ種類の、設計を縛る構造的な事実。**機能の善し悪しとは別に、
これを超えるとサイトが更新できなくなる。**

### 何が起きたか

Vercel の無料枠のうち**デプロイメントストレージだけが上限を超えた**（10.26 GB / 10 GB）。
他のメーター（CPU・関数呼び出し・帯域）はいずれも1%未満で、逼迫していたのは容量だけ。

**Vercel はデプロイ1本ごとに、そのとき事前生成したページを丸ごと保管する。**
当時の内訳は1本あたり214MB:

| | 容量 |
|---|---|
| 選手ページ548人 | 100.1 MB |
| **未消化の試合ページ350件** | **85.2 MB** |
| 消化済みの試合ページ30件 | 11.0 MB |
| その他すべて（フォント5.2MBを含む） | 約18 MB |

**まだ1試合も行われていない350試合のページが40%を占めていた。**中身は日程と
予想フォーメーションだけなのに1件249KB。データ更新は1日6本デプロイするので、
**1日1.3GBずつ増えていた。**

### 決めたこと

**事前生成するページを、シーズンを通して件数が変わらない集合に限る。**

- `getPrerenderedMatchIds()` — 直前の節と進行中の節（20試合）
- `getPrerenderedPlayerIds()` — 日本人選手9人と、4つのランキングの上位（37人）

**「消化済みの試合だけ」では駄目だった。**5月には消化済みが380件になり、元に戻る。
件数が増えない定義でなければ、同じ問題が季節をまたいで戻ってくる。

959ページ → 88ページ。デプロイ1本 **214MB → 約30MB**。

### 失ったもの

**`npm run build` が「全ページを描画して、どれも落ちないことを証明する」テストでなくなった。**
871ページに build 時の網がかからない。`npm run smoke` が標本で埋めているが、全数ではない。
[CLAUDE.md](../CLAUDE.md) の「完了の定義」を参照。

読者側で失われた機能はない。集合の外のページも `dynamicParams` の既定（true）で
初回リクエスト時に描画され、以後キャッシュされる。実測で初回 0.28〜0.44秒、
2回目以降 0.02〜0.05秒。存在しないIDは従来どおり404。

### Vercel 側の設定（リポジトリからは見えないので、ここに書いておく）

**保持ポリシー**（Settings → Build and Deployment → 展開保持ポリシー）を 2026-09-10 に設定した。
既定は4項目とも30日間だった。

| 項目 | 設定値 |
|---|---|
| キャンセルされた配備 | 1日 |
| エラーが発生したデプロイメント | 1日 |
| プレビュー | 1週間 |
| 本番 | 1週間 |

失敗したビルドの成果物は、結果を読んだ後は価値がない。プレビューは PR が開いている間しか
使わない。本番1週間なら約42本残り、30MBのビルドで合計1.3GB程度に収まる。

**この設定はリポジトリに現れない。** 容量がまた増えたときは、まずここを確認すること。

### `vercel remove --safe` はプレビューを消さない

古いデプロイの一括削除には `npx.cmd vercel remove premier-fan-data --safe --yes` を使った。
**`--safe` は「エイリアスが付いたデプロイ」を除外する**が、**プレビューにもプレビューURLという
エイリアスが付いている**ので対象外になる。実際に消えたのは本番だけだった（現在の本番は残る）。

プレビューを消す手段は、実行時点では見つかっていない。

- **デプロイ一覧の行メニューに Delete が無い**（本番・プレビューとも）。
  Instant Rollback / Promote / Redeploy / Inspect / View Source / Copy URL / Assign Domain / Visit のみ
- `--safe` を外すと現在の本番まで消える

**結論: プレビューは保持ポリシーに任せる。** 1週間で自動的に消える。

### 今後ページを増やすときの判断基準

**新しい動的ルートを作るときは、事前生成する集合が件数で上限を持つかを先に決める。**
「全部」と書いた瞬間に、そのルートはデータの増加ぶんだけデプロイを太らせる。

## 8. やらないこと

判断を後から蒸し返さないために明記する。

- **リアルタイム速報・ライブスコア** — 更新が4時間ごと。速報を装えば、試合中に開いた読者に古いスコアを見せて信頼を失う
- **移籍・負傷・出場停止情報** — データが一切ない。手作業で維持すれば必ず更新が止まり、古い情報が残るほうが無いより有害
- **ニュース記事・コラム・戦術解説** — 人手の執筆が入った瞬間、更新頻度がボトルネックになる。日本語の付加価値は「文章を書くこと」ではなく「データを日本語で正しく見せること」に限定する
- **順位予測・勝敗予想・優勝確率** — 3節分のデータで予測を出しても外れる。当たらない予測はサイト全体の数字の信頼まで巻き添えにする
- **他リーグ・他大会** — データがプレミアリーグのみ。範囲を広げると製品ゴールが薄まる
- **動画・ハイライト・画像** — 権利の問題。権利のあるエンブレム以外は扱えない
- **PC向けレイアウトの作り込み** — 読者はスマホで開く。PCで壊れないことは保証するが専用の最適化はしない
- **ユーザーアカウント・通知・コメント** — 運用負荷と、内容が薄いうちに作っても使われないという二重の理由

## 9. 保留 — やらないとは決めていないもの

「やらないこと」に混ぜると判断が固まってしまうため、分けて置く。

- **時間帯の傾向（立ち上がり／終盤）** — 得点・失点イベントに分が入っているので導出できる。
  ただし3節では母数が足りず、10節未満で出すと「たまたま」を傾向として見せることになる。
  10節以降に再検討する
- **ダークモード** — 色トークンは一箇所に集約済みで、後から入れられる。
  デザインの方向が固まる前に検査の手間を2倍にしないため、S18 の後に再検討する
- **過去シーズンの試合スタッツの埋め戻し** — 取得は可能だが1日100リクエスト制限で5日前後かかる

## 10. 着手前に確認が必要なこと

### 実データ検証で判明した訂正

1. チームスタッツは「30試合すべてに39カテゴリ」ではなく、**1試合が16カテゴリしかない**。欠けているのが Expected Goals・Expected Assists・Key Passes・Tackles・Dribbles・Aerial Duels・Crosses など23項目で、S10 のチームスタイル分析が依存する項目そのもの
2. H2H は「190ペア全て揃う」ではなく、**20ペアが履歴ゼロ**（対戦数の幅は 0〜14）
3. 監督名は `Team.coach` が20クラブすべて `null`

### 未解決の確認事項

- **39カテゴリの欠損率がシーズンを通してどうなるか** — 30試合の時点で既に1試合欠けている。S10 はこのデータに全面依存するので、欠損時の扱い（そのカテゴリを非表示にするか、母数から除外するか）を先に決める必要がある
- **「ベンチ入りしたが出番なし」判定の精度** — 4状態分類のうち②③の区別は控えリストへの記載有無から導出する。名前の照合が省略形・愛称・翻字揺れをフォールバックで吸収する構造なので、控えリストに載っているのに照合できず「メンバー外」と誤表示される選手がいないか、日本人選手9人で実データ確認が要る。誤表示が起きるなら②③を統合する
- **選手名の日本語表記をどこから得るか** — 日本人9人とクラブ名20件は手作業で確定できるが、548人ぶんは現実的でない。S01 のスコープを決める前に必要な判断
- ~~**昇格組3クラブの特定**~~ — **解決済み。** 昨季の1部・2部の最終順位表が取れるので、今季の20クラブのうち昨季2部にいた3クラブとして導出できる。ブランクの年数（何年ぶりの1部か）だけは引き続き手入力
- **選手の背番号** — ラインナップ内の `LineupPlayer.number` にはあるが、ロースター全体の `Player` にはフィールドがない。取れなければ選手一覧はポジション順で設計する
- **H2H履歴の深さの基準** — 1試合しかないペアで「過去の対戦成績」を出すと誤誘導になる。何試合以上を意味のある履歴とみなすか。<br>**判明: 記録は2020年1月以降しかない**（全1,417試合の最古が 2020-01-01、内訳はプレミアリーグと2部のみでカップ戦は含まない）。そのため**対戦数は因縁の指標にならない** — マンチェスター・ダービーは11試合で、アストン・ヴィラ対ブライトンの14試合より少ない。多いことは「2020年から両方1部に居続けた」以上の意味を持たない
- **CL出場枠が4か5か** — リーグ係数により変動する年がある。データから導出できないので固定値として持つ必要があり、S03 のバッジ表示に必要
- ~~**過去シーズンのデータ取得可否**~~ — **解決済み。取れる。** football-data.org は 2023/24 以降の最終順位表を返す（2022/23 以前は 403）。1部・2部とも取得可能で、昇格組3クラブの昨季も埋まる。確定値なので4時間更新の対象外とし、`scripts/ingest-past-seasons.mjs` を年1回手で実行する。<br>Highlightly も昨季の試合に39カテゴリ全部を返すため、リーグ平均比の基準を過去シーズンで安定させることも可能。ただし1日100リクエスト制限があり、380試合の埋め戻しには5日前後かかるので現時点では見送っている
