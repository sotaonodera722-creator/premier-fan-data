# 進め方 — 誰が何を決めるか

このプロジェクトは5つの役で回す。役を分けている理由は分業ではなく、
**作った本人に判定させないため**である。

---

## 役

| 役 | 誰 | 成果物 | 決めてよいこと |
|---|---|---|---|
| **代表** | あなた | 承認 | 何を作るか、何を作らないか、優先順位 |
| **マネージャー** | セッション本体 | 実装、統合、報告 | 実装の手順、技術的な選択 |
| **設計** | `sprint-designer` | `docs/sprints/S◯◯.md` | 契約の中身（範囲の判断は代表に上げる） |
| **採点** | `qa-reviewer` | 判定＋指摘 | 合否 |
| **検算** | `data-auditor` | 判定＋指摘 | 合否 |

採点と検算は**同格**で、どちらか一方でも不合格なら不合格。平均で救済しない。

## 採点と検算の境界

| | `qa-reviewer` | `data-auditor` |
|---|---|---|
| 見るもの | ブラウザで見えるもの | 数字そのもの |
| 道具 | Browser | `npm run audit` と `npx tsx` |
| 「三笘の出場時間 90分」を | 表示崩れがないかだけ見る | 実際に90分かを検算する |

**間違った数字はブラウザ上で完璧に見える。** これが役を2つに分けている理由。

---

## 流れ

```
                    ① 契約の承認
   代表 ─────────────────────────────────→ 実装
    ↑                    ↑                    │
    │              sprint-designer             │
    │                                          ↓
    │                              ┌─ qa-reviewer（見た目）
    │              ② 最終判定       ├─ data-auditor（数字）
    └──────────────────────────────┴─ 差分修正 ─┘
```

**承認は2点だけ。** ①で範囲を確定させ、②まではマネージャーが回す。
途中の細かい判断は聞かない。

### ① 契約の承認

`sprint-designer` が `docs/sprints/S◯◯.md` を書き、代表が承認する。
承認欄が空のまま実装に入らない。

代表が見るのは3つ。

1. **「含まない」が妥当か** — ここが契約の本体。作らないものの確認
2. **完了条件が「できた」の定義になっているか**
3. **節7「代表に確認したいこと」への回答**

### 実装

マネージャーが実装する。契約の「含む」だけを作る。
契約にないものを思いついたら、作らずに次のスプリントの候補として書き留める。

### ゲート（実装完了の定義）

検査に出す前に、これが全部通っていること。**通っていないものを検査に出さない。**

```bash
npm run lint && npm run build && npm run audit
```

型エラーで落ちるコードに検査エージェントのターンを使うのは、ただの浪費である。

### ② 検査と最終判定

`qa-reviewer` と `data-auditor` を**並列で**起動する。見るものが違うので競合しない。
どちらにも契約 (`docs/sprints/S◯◯.md`) を渡す。

不合格が出たら差分修正して再検査。2回目以降の検査は**全体を再スキャンさせない** —
前回の指摘が直っているかと、その修正が他を壊していないかだけを見せる。

両方が合格したら、代表に報告する。

#### 「保留（ターン上限）」が返ってきたら

検査エージェントには上限がある（`qa-reviewer` 20 / `data-auditor` 15）。**上限に達したら
超過せず止まり、`保留` を返す。** `合格` でも `不合格` でもない第三の答えで、
**合格として扱ってはならない。**

保留が返ったら、報告に載っている「確認できていないこと」だけを渡して再起動する。
新しい検査ではなく、同じ検査の続きなので、確認済みの項目は二度と見せない。

上限を上げるのではなく範囲を絞るのは、超過の原因が上限の低さではなく、
**依頼が絞れていないこと**だからである。対象URLと測る値まで書いて渡せば、
エージェントは探索にターンを使わずに済む。

### 検査後 — ここを飛ばさない

1. 両エージェントが出した「qa-log 追記用エントリ」を `docs/qa-log.md` に**追記する**
2. 再発防止リスト（R番号）に足すべき症状があれば足す
3. 持ち越し項目を、次のスプリント契約の候補として `docs/sprints/` に残す

**この3つを飛ばすと、検査は毎回ゼロから始まることになる。** 過去に一度出した不具合を
二度出さないための仕組みはここにしかない。

---

## この体制で守ろうとしているもの

- **作った本人が採点しない** — `CLAUDE.md` の「自己評価の扱い」
- **数字の正しさが誰かの担当である** — 見た目のレビューでは原理的に見えない
- **範囲を後から広げない** — 契約の「含まない」を検査者も読む
- **指摘が消えない** — `qa-log.md` に残り、次の検査の入力になる
- **高い検査の前に安い検査を通す** — lint / build / audit
